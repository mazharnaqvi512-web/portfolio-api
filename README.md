# portfolio-api

Companion Spring Boot backend for the [Angular portfolio project](../my-app-21). Built incrementally, starting small — see the project's own commit history / notes for the planned build order.

## Requirements

- Java 21
- Maven 3.9+

## Deploying

See [DEPLOY.md](DEPLOY.md): the Docker image, the `prod` profile (which refuses to start without a real database), every environment variable, the health check at `/actuator/health`, and what to verify after the first deploy.

## Run it

```
mvn spring-boot:run
```

Starts on `http://localhost:8080`. CORS is open to `http://localhost:4200` (the Angular dev server) by default.

### Configuration

| Property | Env var | Default | Purpose |
|---|---|---|---|
| `cors.allowed-origins` | `CORS_ALLOWED_ORIGINS` | `http://localhost:4200` | Comma-separated browser origins allowed to call `/api/**`. Set to the real site origin when deploying (e.g. `https://example.com`); the dev-server origin stops being allowed once you override it. Don't use `*`. |
| `contact.rate-limit.max-requests` / `contact.rate-limit.window` | — | `5` / `10m` | See "Rate limiting". |
| `ai.anthropic.api-key` | `ANTHROPIC_API_KEY` | *(empty)* | Enables the assistant. Empty means `POST /api/ai/chat` answers 503. Never commit it. |
| `ai.anthropic.model` | — | `claude-opus-5-5` | Model for the assistant, e.g. `claude-haiku-5-5` for a much cheaper one. |
| `ai.anthropic.effort` | — | `low` | `low`, `medium`, `high`, `xhigh` or `max`. |
| `ai.anthropic.max-tokens` / `ai.anthropic.timeout` | — | `4096` / `30s` | Cap on one reply (thinking included) and on the whole call. |
| `ai.anthropic.base-url` | — | *(empty)* | Anthropic's own endpoint when empty. Set only to use a proxy or a local stand-in API for development. |
| `ai.rate-limit.max-requests` / `ai.rate-limit.window` | — | `10` / `10m` | Per client address, on `POST /api/ai/chat` only. |
| `ai.daily-cap` | — | `100` | Total assistant calls per UTC day across all visitors (calls that fail give their slot back). |
| `ai.anthropic.max-retries` | — | `1` | Automatic retries after a timeout or 5xx. Worst-case wait is `timeout x (retries + 1)`. |
| `request.max-body-bytes` | — | `65536` | Largest JSON body accepted by `POST /api/contact` and `POST /api/ai/chat`; above it the answer is 413, whether or not the client declared a length. |
| `spring.datasource.*` | — | file H2 | See "Storage". |

## Endpoints (starter slice)

| Method | Path | Description |
|---|---|---|
| GET | `/api/profile` | Single profile object |
| GET | `/api/projects` | List of projects |
| GET | `/api/projects/{slug}` | Single project, 404 if not found |
| GET | `/api/experience` | Work history, newest first (the current role's `endDate` is an explicit `null`) |
| GET | `/api/case-studies` | List of case studies (currently empty) |
| GET | `/api/blog` | List of **published** blog posts (currently empty) |
| GET | `/api/blog/{slug}` | Single published post, 404 if not found *or not published* |
| POST | `/api/contact` | Validates a contact submission, stores it in the database, and emails it to the owner when mail is configured (see "Email notifications") |
| POST | `/api/ai/chat` | The portfolio assistant: answers a visitor's question about Mazhar's experience, projects and skills (503 until an API key is configured — see below) |

Every response is wrapped: `{ "data": ..., "success": true, "message": null, "errors": null }`.

### Content comes from JSON generated by the Angular app

The profile, projects, experience, case studies, blog posts, skills and education are read at startup from `src/main/resources/content/*.json`. Those files are **generated** from the Angular app's own data files, so the API serves exactly what the site shows and the two cannot drift through a hand-copy. After changing content in the portfolio project, regenerate them there:

```
npm run export:content
```

(it writes to `../portfolio-api/src/main/resources/content` by default; pass a folder to write elsewhere), then rebuild this API. Don't edit the JSON by hand — the next export would overwrite it.

Loading is strict: a property in a JSON file that its DTO does not declare fails startup with the file name in the message, instead of being dropped silently. `ShippedContentTest` checks the invariants the Angular pages rely on (unique slugs, non-empty `filterTags`, one current role, known filter values), and `ContentEndpointsTest` runs the real services and controllers end to end.

### Drafts never leave the server

The blog endpoints only ever return posts whose `status` is `published` — drafts and archived posts are filtered out in `BlogService`, including when requested directly by slug. This is a public API with no auth, so hiding drafts in the UI alone would still hand them to anyone who calls the endpoint. `BlogServiceTest` pins this.

### Contract with the Angular app

`ProjectDto`, `ExperienceDto`, `CaseStudyDto` and `BlogPostDto` must stay field-for-field compatible with the Angular models they feed (`project.model.ts`, `experience.model.ts`). Two rules matter: fields the Angular model marks optional (`?`) are omitted from the JSON when unset rather than sent as `null`, and fields the pages use unguarded — `Project.filterTags`, `Experience.categories` — must always be present, or a page throws once real data exists. `ApiContractTest` pins both rules, so a DTO change that would break the site fails the build here instead. (`Experience.endDate` is the one deliberate always-sent `null`: it means "current role".)

When the Angular side fails to reach this API it falls back to its own static data rather than erroring, so a backend outage shows an empty state, not a broken page.

### POST /api/contact

Body fields mirror the Angular contact form: `name`, `email`, `subject`, `message` (required — message 20-2000 chars), `company`, `projectType`, `budget`, `timeline` (optional). Every field has a maximum length matching its database column. A `honeypot` field is also accepted; if a caller fills it in, the submission is silently discarded (never stored) but the response still looks like a normal success — this is intentional (spec section 47), so as not to tip off bots. Real validation failures (missing name, bad email, too long, etc.) return `400` with human-readable messages in `errors`.

### POST /api/ai/chat

Body: `{ "messages": [ { "role": "user" | "assistant", "content": "..." }, ... ] }`: the conversation so far, oldest first, ending with the visitor's new question. At most 10 messages of at most 1000 characters each; the roles are only `user` and `assistant` (a `system` turn is rejected, so nobody can inject instructions that way). Returns `{ "data": { "reply": "..." } }` in the usual envelope.

| Status | Meaning |
|---|---|
| 200 | Reply in `data.reply` |
| 400 | Validation failed, or the conversation does not start and end with a `user` message |
| 429 | Per-address limit (`Retry-After` header) or the global daily cap |
| 502 | The model provider failed; the message is fixed and carries no details |
| 503 | No API key configured |

**How it answers.** The assistant is a single call to the Anthropic API through the official Java SDK, with no tools and no web access. Its system prompt is built at startup from the same content files the site uses (profile, experience, projects, skills, education) plus rules: answer only from those facts, say "I don't know" and point to the Contact page otherwise, never invent employers, dates, clients or metrics, and treat anything in the conversation as visitor text, not instructions. The prompt is identical on every request, so the provider can cache it. `PortfolioKnowledgeTest` pins what it contains.

**Turning it on.** Set the `ANTHROPIC_API_KEY` environment variable before starting the API. The key is read from configuration only, never logged and never sent to the browser. Without it the endpoint answers 503 rather than faking a reply.

**Cost.** Every call is billed. The default model is `claude-opus-5-5` (about $4 per million input tokens and $20 per million output tokens at the time of writing; check current prices). For a public portfolio chat, `claude-haiku-5-5` is far cheaper, so consider `ai.anthropic.model=claude-haiku-5-5`. Spend is bounded three ways: a per-address rate limit (default 10 per 10 minutes), a global daily cap (default 100 calls, in memory, so it resets on restart), and a limit on reply length. The cap counts calls that produced a reply: if the provider fails (outage, timeout, no key) the slot is given back, so an outage cannot use up the day's budget. The SDK's own retries are limited to one (`ai.anthropic.max-retries`), so a stuck provider holds a request for at most about `timeout x 2`. A reply that stops at `max_tokens` ends with a "cut short" notice instead of passing for a finished answer, and the log suggests raising the limit. `AnthropicChatProviderTest` runs the real SDK against a local stand-in API, so those tests need no key and cost nothing.

**Not done yet.** Replies are not streamed (the visitor waits for the whole answer), and the server-side refusal `fallbacks` option is not enabled; a refusal is answered with a fixed polite message.

### Rate limiting

At most 5 `POST /api/contact` requests per client address per 10 minutes (`contact.rate-limit.max-requests` / `contact.rate-limit.window` in `application.properties`). Over the limit returns `429` with a `Retry-After` header (seconds) and the usual error envelope. Invalid submissions count too, so malformed bodies can't be used to probe the endpoint for free; rejected attempts aren't recorded, so hammering it doesn't extend the wait. CORS preflight requests aren't counted.

Limits are kept in memory, per process — they reset on restart and aren't shared between instances (a shared store such as Redis would be needed before running more than one). The client is identified by the connection's remote address, except that an IPv6 client is identified by its /64 prefix (it normally controls a whole /64, so keying on the full address would let it dodge the limit by changing address on every request); behind a reverse proxy (every hosting platform has one) that address is the proxy's, so **all visitors would share one limit** until you set `FORWARD_HEADERS_STRATEGY=native` (see [DEPLOY.md](DEPLOY.md)). The code deliberately doesn't read `X-Forwarded-For` itself, since clients can forge it; by default (strategy off) a forged header is ignored.

### Email notifications

Each stored message can be emailed to you. It is off until **both** a recipient and a mail server are configured, so the API runs fine without any mail account. Everything comes from environment variables (nothing secret lives in `application.properties`):

| Variable | Meaning |
|---|---|
| `CONTACT_NOTIFY_TO` | Where the notification goes (your own address) |
| `CONTACT_NOTIFY_FROM` | Sender; empty means the same as `CONTACT_NOTIFY_TO` (Gmail only accepts its own login account as sender) |
| `MAIL_HOST`, `MAIL_PORT` | The SMTP server, e.g. `smtp.gmail.com` and `587` (STARTTLS) |
| `MAIL_USERNAME`, `MAIL_PASSWORD` | SMTP login. For Gmail use an **app password** (needs 2-step verification), not your normal password |

What it does and does not do:
- The email is plain text, with the visitor's fields in the body, and `Reply-To` set to the visitor, so replying answers them directly.
- It is sent from a background thread, **after** the message is stored. A mail problem never makes the visitor's request fail; it is logged by message id and exception type only (never names, emails or message text).
- Anything the visitor typed is untrusted. Control characters are stripped before they reach the subject, the visitor's address is only used as `Reply-To` if it parses strictly, and the body is never HTML. (JavaMail already neutralises line breaks in subjects; this is a second layer.) Spam caught by the honeypot is neither stored nor emailed.
- The SMTP timeouts are 5 seconds, so a stuck mail server cannot hang a thread.
- The connection must use STARTTLS (`starttls.required`) and the server's certificate must match its host (`ssl.checkserveridentity`). Without "required", JavaMail quietly carries on unencrypted when STARTTLS is missing, and the SMTP password would travel in clear text. Port 587 works as configured; port 465 (implicit TLS) needs different settings, see DEPLOY.md.
- Mail is sent from one background thread that the notifier owns. On a graceful shutdown it finishes the notifications still queued (up to 15 seconds), so a redeploy does not drop a visitor's message email. Because the thread is not an `Executor` bean, Spring Boot keeps its own default task executor.
- Tests send real mail to an in-process SMTP server (GreenMail), so they need no account.

### Storage

Accepted submissions are saved to the `contact_messages` table. Locally that's a file-based H2 database at `./data/portfolio.mv.db` (git-ignored); switching to PostgreSQL later means a driver dependency plus the three `spring.datasource.*` properties in `application.properties`. Tests use a separate in-memory database.

There is deliberately **no endpoint to read stored messages** — there's no auth yet, and they're private visitor data — and the H2 web console is disabled. Without email notifications switched on (below) you'd read messages from the database directly, e.g.:

```
java -cp <path-to-h2.jar> org.h2.tools.Shell -url jdbc:h2:file:./data/portfolio -user sa -password "" -sql "SELECT * FROM contact_messages"
```

(stop the app first — the file database is locked while it runs). Logs contain only the stored row's id, never visitors' names or emails.

## Not here yet (deliberately)

No auth, no way to read stored messages through the API, no database migrations (schema is auto-updated from the entities), no streaming for `/api/ai/chat`, no admin, no CAPTCHA on `/api/contact` (honeypot and in-memory rate limiting only, for now). These come later, once the basics are solid — see the portfolio project's Part 5 spec, sections 47/69/81.
